# Фильтры User Explorer

**User Explorer** — основной инструмент поиска и сегментации пользователей в CRM плагина `local_subscriptions`.

Он помогает формировать рабочие списки для поддержки, продаж, удержания и анализа.

## Архитектура фильтрации

Функция должна сохранять разделение ответственности:

1. repositories выполняют SQL, сортировку и пагинацию;
2. services рассчитывают бизнес-статусы;
3. renderers подготавливают данные для интерфейса.

Templates не должны содержать SQL или сложные бизнес-правила.

## Текстовый поиск

Поиск может учитывать:

- отображаемое имя;
- основной e-mail;
- тему сообщения;
- внутренний идентификатор;
- индексируемые поля CRM.

Нормализация регистра должна выполняться с помощью совместимых методов Moodle.

## Коммерческие статусы

Типичные фильтры:

- активный пробный период;
- завершенный пробный период;
- покупка курса;
- активная подписка;
- истекшая подписка;
- lifetime-клиент;
- доступный upgrade;
- проблема с платежом.

Статусы должны рассчитываться сервисами.

## Фильтры активности

Можно находить:

- недавно активных пользователей;
- неактивных пользователей;
- пользователей без входов;
- профили с недавней CRM-активностью;
- пользователей без контакта за выбранный срок.

Все даты должны учитывать часовой пояс Moodle.

## Сегменты CRM Intelligence

CRM Intelligence может открывать User Explorer с готовым набором фильтров.

Примеры:

- профили риска;
- пробные пользователи с высокой вероятностью покупки;
- пользователи для повторного контакта;
- неуспешные платежи;
- диалоги без ответа;
- незавершенный onboarding.

Интерфейс должен явно показывать активный сегмент.

## Фильтры Digital Purchases

Можно фильтровать по:

- тарифу;
- валюте;
- статусу платежа;
- дате покупки;
- типу операции;
- источнику заказа;
- возврату;
- upgrade.

Данные должны совпадать с Dashboard и профилем пользователя.

## Комбинирование

Независимые фильтры обычно соединяются через **И**.

Пример:

```text
Активный пробный период
И
Нет покупки
И
Нет активности более 7 дней
```

Несколько значений внутри одной группы могут использовать **ИЛИ**.

## Сортировка и пагинация

Сортировка должна выполняться в SQL до пагинации.

Полезные варианты:

- последняя активность;
- дата регистрации;
- последняя покупка;
- общая сумма;
- уровень риска;
- имя.

Сортировка только в браузере недостаточна.

## Безопасность

Доступ защищается capability Moodle.

Чувствительные действия должны проходить через `AdminSecurity`.

Ссылки должны использовать `moodle_url` и маршруты `subscription_config`, если они предусмотрены.

## Сброс фильтров

Полный сброс должен:

- очистить параметры поиска;
- удалить сегмент, полученный из Dashboard;
- вернуть первую страницу;
- восстановить сортировку по умолчанию;
- удалить скрытые параметры URL.

## Диагностика

Если профиль не найден:

1. сбросьте фильтры;
2. найдите точный e-mail;
3. проверьте статус Moodle-аккаунта;
4. проверьте права администратора;
5. проверьте покупки и подписки;
6. проверьте даты;
7. очистите кэш после изменения кода.

Ошибки выборки исправляются в repository или service, а не в renderer.
